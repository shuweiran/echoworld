## 一、现状调研（源码取证）

### 1. 一般模式（free/director/protagonist/multi_track/werewolf/script）轮次执行链

```
SessionController /api/send、/api/round/start
  → RouterService.runRound(userInput, userInterjection[, speaker])      （service/RouterService.java，禁动）
      Step 2  Arbiter.configureTracks（轨道配置，LLM）
      Step 3  AgentExecutor.executeRound(config, agentMap, ctxBuilder)   （agent/AgentExecutor.java）
              → 全部 agent 各自虚拟线程并行调用 LLM（AgentExecutor 设计初衷：5 agents = 1x LLM delay）
              → 每个 agent 的上下文由 ctxBuilder（= RouterService.buildAgentContext）在任务内构建
      Step 4  收集输出 → memory.addMessage(每 agent 输出) → SSE agent_output 逐个推送
      Step 5  Arbiter.integrateOutputs（主控整合旁白）
```

### 2. 「同轮上下文不共享」断点定位

- **上下文来源**：`RouterService.buildAgentContext(agentName, trackMode, trackId)`（RouterService.java 中段）——
  identity（人设）+ 场景 + 剧本杀角色卡（仅 script 模式）+ 轨道 + `memory.getSummaryContext()` + `memory.getAgentContext(agentName, 30)`（**对话历史，只含上一轮及以前的消息**）。
- **同轮输出写入时机**：`executeRound` 返回后，RouterService Step 4 才把各 agent 输出 `memory.addMessage(...)` 落史。并行阶段内没有任何 agent 能看到本轮其他 agent 的发言。
- **断点 = AgentExecutor.executeRound 的全并行执行 + RouterService Step3→Step4 的顺序**：A、B 同轮发言，B 生成时 A 本轮发言尚未入 memory → B 看不到 A 本轮说了什么（只能看到 A 上一轮及以前的）。
- 对照 2D 世界（ConversationManager.executeRound）：同轮也是并行（CountDownLatch），但 2D 群组有 `group.getMessageHistory()` 且每轮把 responses 经 processResults 记入群组历史、下一轮 prepareContext 才能读到——**跨轮共享成立，同轮不共享**，与本轮要解决的一般模式问题同构。

### 3. 为什么「最小改动」落在 RouterService（禁动）

| 候选改法 | 涉及文件 | 禁动？ |
|---|---|---|
| A. runRound Step3 并行 executeRound → 串行循环：逐个 agent 生成 → 每完成一个立即 memory.addMessage → 下一 agent 的 buildAgentContext 自然读到 | **RouterService**（Step3/Step4 重排）+ AgentExecutor（可不改，直接循环调 agent.generateSync 或复用 executeRound 单任务） | ❌ RouterService 禁动 |
| B. AgentExecutor 新增串行方法 executeRoundSerial（带 onAgentOutput 回调写 memory） | AgentExecutor（非禁动）+ **RouterService 调用点改调新方法** | ❌ RouterService 禁动 |
| C. 完全不动 RouterService，靠前端排序/延迟展示 | 前端 | ✅ 但解决不了「上下文不共享」——后端 LLM 上下文才是问题本体，前端排序只改展示顺序不改生成依据 |

**结论：A/B 都需要改 RouterService（禁动），C 治标不治本。按 AGENTS.md「禁动文件不动，若实现需要动这些文件→停下来写方案报告给主会话决策」停手。**

## 二、推荐方案（授权后实施，最小改动版）

### 改动点 1：RouterService.runRound Step3→Step4 重排为串行循环

将现有：

```java
// Step 3: Execute all agents in parallel
AgentExecutor.ExecutionResult execResult = executor.executeRound(config, agentMap, ctxBuilder);
// Step 4: Collect agent outputs → memory.addMessage
```

改为（保留既有 SSE/中断/指标结构）：

```java
// Step 3-4 (串行)：按轨道顺序逐个生成，每完成一个立即入史（后发言者上下文含前者本轮发言）
List<AgentExecutor.AgentOutput> outputs = new ArrayList<>();
boolean cancelled = false;
for (Track track : config.getTracks()) {
    for (String agentName : track.getActiveAgents()) {
        if (!agentMap.containsKey(agentName)) continue;   // P0-2 speaker 排除逻辑沿用
        String context = buildAgentContext(agentName, trackMode(track), track.getId());
        String content = agent.generateWithContext(context);   // 或带 CancellationToken 的版本
        // 校验非空 → memory.addMessage + SSE broadcastAgentOutput + outputs.add（复用现有 Step4 代码块）
    }
}
```

要点：
- **顺序** = 轨道顺序 × 轨道内 agent 顺序（AgentExecutor.buildTasks 现有排序逻辑：PLAYER > DM > NPC，可沿用 computePriority 保证玩家角色先发言）。
- **上下文累积** = 每个 agent 输出立即 `memory.addMessage`，下一个 `buildAgentContext` 读 `memory.getAgentContext(name, 30)` 即包含本轮前面角色的发言——「后发言者上下文包含前者发言」达成。
- **轨道隔离语义保留**：`memory.getAgentContext(agentName, 30)` 现按角色可见性过滤（若 memory 层已实现轨道可见性过滤，则 WEAK/ISOLATED 角色仍只读自己可见部分；需在实施时核对 MemoryStore.getAgentContext 的过滤逻辑，避免串行化破坏 Track 隔离——这是实施时的关键校验点）。
- **中断/取消**：串行循环内每步前检查 InterruptManager 取消标志（D1 语义保留），被取消则中断循环并走现有 cancelled 分支。
- **性能代价**：5 agents 从 1× LLM delay → 5× LLM delay（回到 Python 旧实现语义）——**这正是「不限速、直接显示」串行语义的代价**，属预期（主人拍板方案明确要求串行）。可后续加配置开关 `roleplay.round.serial`（默认 false 保持并行，授权后按需开启）避免影响现有 272 测试与 2D 并行路径。

### 改动点 2（可选，防回归测试）

新增测试 `RouterServiceSerialRoundTest`（或扩展既有 RouterTest）：
- 用 mock LLM 让 agent 输出包含「我听到了 X 刚才说：<X 的本轮发言>」→ 断言后发言者上下文确实包含前者本轮发言（直接验证上下文内容，mock LLM 断言 prompt 含前者发言文本）。

- 串行顺序断言：输出顺序 == 轨道/优先级顺序。

### 改动点 3（前端）

一般模式（非 2D）前端零改动（ChatPage 直接展示，顺序由后端保证）——已确认无需排队/打字机。

## 三、风险与影响

| 风险 | 等级 | 说明/缓解 |
|---|---|---|
| 串行化后单轮耗时 = 各 agent LLM 耗时之和 | 中（预期内） | 主人方案明确「不限速」；建议配置开关默认并行，串行仅授权后按需启用 |
| 破坏 Track 轨道隔离 | 高（实施关键校验点） | memory.getAgentContext 的可见性过滤必须保持；串行循环里每个 addMessage 后下一 agent 读史仍走同一过滤——需新增测试锁定（改动点 2） |
| 影响 2D/剧本杀讨论（ConversationManager 并行路径） | 无 | 串行化只改 RouterService.runRound，ConversationManager 并行路径零触碰 |
| 影响既有 272 测试 | 低 | 默认并行（开关 false）时行为逐字节不变；串行仅在开关开启时生效 |
| SSE agent_output 时序 | 低 | 串行下仍逐个推送，前端 addAgentMsg 顺序天然正确（甚至更符合「顺序发言」观感） |
