## 一、结论摘要（TL;DR）

**不是渲染层变卡，是 SSE 广播被 P-0815-E 的节流游标 bug 打死了，前端退回 3s 轮询 → 角色每 3 秒跳变一次 = 「更严重了」。**

1. **根因（后端 1 行 bug，已修）**：P-0815-E 的 SSE 节流判定 `snapshot.tick() - lastBroadcastTick >= 2` 依赖跨世界重启的 `lastBroadcastTick` 游标；而 `load-characters/clearAgents` 会把 `tickCount` 归零、`lastBroadcastTick` 却保留旧值 → **新世界 tick 未超过旧世界最后广播 tick 前 SSE 全程静默，静默区随重启次数增长**。8000 上世界反复重启后，SSE 实际已死（实测运行中世界 155s 内 0 条广播；SSE 连接 300s 无事件被服务端超时断开）。
2. **前端渲染层实测健康**：修复后 CDP 实测 60fps 恒定（p50/p90/p99=16.7/16.7/16.8ms，P-0815-F 基线 p99 66.6ms → 现 16.8ms）、0 长任务（>50ms）、主线程 JS busy 仅 5-6%；P-0815-F 的 4 项节流全部按设计工作（redrawLinks=2.5Hz=理论值、setConversations gate bail 95-100%、障碍层/文本缓存归零化）。
3. **修复**：节流判定改为无状态 `snapshot.tick() % 2 == 0`（1 行），免疫重启；8001 受控 A/B 验证：修复前世界重启后 SSE 0 条/8s，修复后三次重启均 21 条/8s 恒 2.5Hz。**该修复已随并行批次 20:04 的重新打包进入 8000 运行实例**（PID 3268，jar 内字节码实证 `iconst_2; irem`，无 lastBroadcastTick 字段）。

## 二、代码复查结论（P-0815-F 4 处节流 + P-0815-E SSE 节流）

### 2.1 SimulationScene.ts（P-0815-F 前三项）—— 逻辑正确，无回归

| 改动 | 复查结论 |
|---|---|
| ①链接层 `redrawLinks` 位置签名置脏 + 100ms 节流 | 正确。签名 = 名+取整坐标；`applySnapshot` 变化置脏、`update()` 按最小间隔消费。数据源 2.5Hz 下实际重绘 ≤2.5Hz（实测 20 次/8s），静止归零。视觉无差异（链接层只消费快照数据）。 |
| ②障碍层签名门控 | 正确。`type/x/y/w/h` 串比对，障碍静态（场景切换/地图注入才变）→ 每快照 5Hz 全量重绘+label 重建归零。 |
| ③setText 缓存（name/emoji/bubble + color） | 正确。比较键 = 渲染值本身（`nameLast/nameLastColor/emojiLast/bubbleLast`），值未变跳过 `setText`（Phaser Text 每次重建纹理）。气泡位置仍每快照更新（廉价，不重建纹理）。 |

### 2.2 PhaserSimulationView.tsx setConversations 门控（P-0815-F ④）

- 比较键 = **长度 + 末条 JSON.stringify**。查证后端 `SimulationWorld.recentConversations` 为**纯追加**结构（`addConversationEntry` 每次 append 新 map，条目不可变，容量 50 窗口滑动），且条目含 `tick` 字段 → **末条相等 ⇔ 内容未变**，「末条相等但中间变化」在追加式数据下不可能发生 → 无误判。
- 实测：SSE 路径 8s 内 22 次调用 21 次 bail（95%），轮询路径 100% bail → 3s 轮询不再触发全量重渲染。
- **遗留观察（非本批引入，P2）**：比较用 `JSON.stringify` 每次 O(末条大小)，50 条窗口下可忽略；若未来条目改为可变/重排序需同步重审。

### 2.3 P-0815-E SSE 广播节流（SimulationController.java）—— **回归根因**

- 原实现 `snapshot.tick() - lastBroadcastTick >= 2` 的 `lastBroadcastTick` 为 controller 级字段，**世界重启不重置**（`SimulationWorld.start()` 每次把 `tickCount` 归 0，但游标保留旧值）。
- 后果：新世界 tick 从 0 起算，需 `tick ≥ lastBroadcastTick+2` 才恢复广播 → 静默期 = 旧世界最后广播 tick × 200ms，**随重启次数线性增长**。长运行服务器（如 8000 自 14:13 起被多轮测试反复重启世界）SSE 实际死亡。
- 附带影响：前端 `/api/simulation/events` 只剩连接时初始快照 + 3s 轮询兜底 → 角色位置每 3s 跳变一次（轮询快照直接 `applySnapshot`，无插值过渡时间）→ 视觉「一卡一卡 / 更严重」。

## 四、根因定论

**P-0815-E 需求 3 的 SSE 广播节流引入跨重启状态 bug**（`lastBroadcastTick` 游标不随世界重启归零），是「更严重了」的直接根因；P-0815-F 的 4 项前端节流经代码复查 + 实测均正确有效，非回归源。前端「卡」的真实机制：

```
SSE 死 → 前端唯一位置更新源 = fetchState 3s 轮询
→ 每次轮询直接 applySnapshot（位置从 A 跳到 B，无 400ms 级插值过渡）
→ 角色每 3 秒跳变 + 对话消息每 3s 才刷新 → 感知「更卡」
```

（注：即使 SSE 正常，P-0815-E 也把位置更新率从旧版 5Hz 降到 2.5Hz——该降频本身在 60fps 渲染 + 速度外推插值下感知轻微，属设计取舍；真正不可接受的是游标 bug 导致的 0Hz。）

## 五、修复（已实施 + 已上线 8000）

**文件**：`src/main/java/com/roleplay/engine/simulation/SimulationController.java`（tick listener）
**改动**（1 行核心 + 注释说明）：

```java
// 旧：if (snapshot.tick() - lastBroadcastTick >= SSE_BROADCAST_TICK_INTERVAL) { lastBroadcastTick = ...; ... }
// 新：无状态判定，免疫世界重启
if (snapshot.tick() % SSE_BROADCAST_TICK_INTERVAL == 0) {
    event.put("recentConversations", world.getRecentConversations());
    broadcastToAll(event);
}
```

- 同时删除已无引用的 `lastBroadcastTick` 字段。
- 语义：每偶数 tick（=每 2 tick=400ms）广播，恒 2.5Hz，与设计意图一致；tick 从 0 起连续自增，偶数 tick 必然存在。
- **验证**：`mvn compile EXIT=0`；8001 受控 A/B（§3.2）三次重启恒 2.5Hz；**8000 已生效**（并行批次 20:04 重新打包主 jar，字节码实证 `iconst_2; irem`、无 lastBroadcastTick 字段，PID 3268）。
- 禁动文件检查：RouterService/ArbiterService/审批/狼人杀/剧本杀 Service 零改动；SSE 主链路为任务明确授权范围（本批即调查其节流改动）。

## 六、其他瓶颈顺查（无新问题）

1. **Phaser 每帧开销**：update() 内 = 插值收敛循环（≤8 agent）+ 接近提示（廉价格）+ 链接层节流消费；每快照 = computeBubbleLanes（≤8 条排序）+ renderAgent×N（graphics 操作）。实测 JS busy 5-6% → 无瓶颈。
2. **React 3s 轮询重渲染**：fetchState 内其余 setState（setRunning/setCurrentScene）值不变 → React bail；唯一重量级 setConversations 已被门控（100% bail）。`worldMsgs` useMemo 依赖 `[conversations, bump]` 在打字机逐字时重算，但 ≤50 条遍历成本可忽略。
3. **SSE 400ms 节流本身**：2.5Hz 快照 + 前端速度外推插值（P-0814-B 的 `vx*dt` 外推）下移动平滑；仅角色转向/停走瞬间有轻微阶梯感（可接受）。
4. **素材动画**：console 无新增错误；既有 charanim-助手 素材解析错误为素材库资产问题（非本批引入，P2）。
