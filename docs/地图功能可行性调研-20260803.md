## 一、调研项 1：创建剧本时同步创建对应剧本地图 + 内嵌进剧本

### 1.1 现状核实（证据）

**a) 生成剧本时是否已自动同步生成地图？——否，必须手动点「生成地图」。**

- 剧本生成唯一路径：`POST /api/script/init`（`controller/ScriptController.java:79-118`）→ `ScriptGameService.initGame`（`service/ScriptGameService.java:325-405`）。initGame 内仅调用 `scriptService.generateScript(theme, playerNames)`（`:331`）生成剧本 schema，**全程无任何地图生成调用**（grep initGame 全函数无 generateMap）。
- 另一条剧本生成端点 `POST /api/session/script/generate`（`controller/SessionController.java:291-300`）同样只返回剧本 JSON（generateScript 输出），无地图。
- 地图唯一生成入口：`POST /api/script/map`（`ScriptController.java:125-139`）→ `ScriptGameService.generateMap`（`ScriptGameService.java:498-522`）。前端仅 ScenePage 剧本杀 Tab「🗺️ 生成地图」按钮手动触发（`components/ScenePage/ScenePage.tsx:743-745`，逻辑 `genScriptMap` `:375-398`）。
- 前端生成剧本链：`genScript`（`ScenePage.tsx:315-337`）→ 成功 → `startScript(game)` 自动进对局（P0-5 两步式改一步式已落地）——**但没有自动 `genScriptMap()`**。未生成地图时卡片区显示占位「尚未生成地图——点击『生成地图』…」（`ScenePage.tsx:769-770`）。

**b) 地图数据是否内嵌在剧本 schema（ScriptSchemaV1）里？——否，独立字段 + 独立存储。**

- `ScriptSchemaV1`（`docs/剧本-schema-v1.md` 字段表）**无 map 字段**；`ScriptSchemaV1.java` 全文件 grep 无 map 相关业务字段（仅 import java.util.Map）。
- 地图挂在 `ScriptGame.mapData` 字段（`ScriptGameService.java:184`，ScriptGame 内部类非 schema 字段）；`toMap` 在 mapData 非空时附加顶层 `map` 键（`:227-228`）——即地图随 `GET /api/script/status` 下发，但那是「对局视图附加键」，不是剧本 JSON 的一部分。
- 落库分离：对局快照（type=snapshot）含 `map_data`（`saveSnapshot` `:1776`，恢复 `:1840`）；**剧本落库（type=script）不含 map**（`persistScript` `:1431-1458` 字段清单无 map_data）。即「剧本」与「地图」在存储上是两笔记录。

**c) 一致性保障现状（地图与剧本主题/地点/线索的衔接，已有什么）：**

- 地图 prompt 注入剧本上下文：`ScriptMapService.buildPrompt`（`ScriptMapService.java:178-226`）把 theme + `game.locations` + 线索地点去重列表注入 LLM 地图生成 prompt，要求 `zones[].clue_location` 逐一取自线索地点。
- theme 缺省回退剧本名：`generateMap` 中 `effTheme = theme 空 ? game.name : theme`（`ScriptGameService.java:505`）。
- 生成后归一绑定：`bindClueLocations`（`ScriptMapService.java:124-152`）把 zone.clue_location 宽容映射回剧本标准地点（精确 → trim → 子串双向 → 同义词表，`matchLocation` `:155-175`）。

**d) 缺口清单（完成度差额）：**

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G1-1 | **无自动串联**：init/generate 均不自动生成地图 | `ScriptGameService.java:331`（initGame 仅 generateScript）；前端 `genScript` 无 genScriptMap 调用（`ScenePage.tsx:315-337`） | 剧本生成 ≠ 有地图；「无地图兜底剧本」常态存在（但游戏可玩——ChatPage 面板按地点搜证不依赖地图，地图是增强入口） |
| G1-2 | **schema 无 map 字段**：地图不在剧本 JSON 内 | `docs/剧本-schema-v1.md` 字段表；`ScriptGameService.java:1431-1458` persistScript 无 map_data | 「内嵌进剧本」需动 schema v1（版本内嵌 JSON 纪律允许加可选字段，宽容解析兜底，无需表结构变更） |
| G1-3 | **LLM 地图 maxTokens=800 疑似不足**（对照 D-023 同款缺陷） | `ScriptMapService.java:81` `callJson(prompt, 800)`；D-023 实证：4 角色剧本 JSON 需 2000-4000 tokens，600 被硬截断致 3/3 走兜底 | 地图 JSON 含 ground+collision 双层数组（20-32×14-20 格 ≈ 560-1280 个数字）+ rooms/zones/spawns，**逻辑估算输出 1300-2000+ tokens > 800** → 截断 → 校验失败/JSON 解析失败 → **大概率频繁 BSP 降级**。「LLM 生成地图」路径实际可能以 BSP 为主。置信度：中-高（逻辑推断，测试用 mock LLM 不覆盖真实 token 量，建议真机验证一次） |
| G1-4 | **BSP 兜底地图与剧本完全脱钩** | `BspMapGenerator.java:107` 房间名「房间 A/B/C…」、`:168` `zone.clue_location = room.name()`；`LOCATION_SYNONYMS`（`ScriptMapService.java:48-60`）无「房间 A」类键 | BSP 地图 zone 的 clue_location 无法归一到剧本标准地点 → 地图上点击搜证必返回「该地点没有更多可搜证线索」（前端搜索用 zone.clue_location，`PhaserScriptMapView.tsx:52-62`）。ChatPage 面板搜证不受影响（按 locations 列表） |
| G1-5 | **无 zone 覆盖保证**：zone 数 < 线索地点数时部分线索地点在地图上无入口 | `MapValidator` 7 项校验（`MapValidator.java`）不含「线索地点覆盖率」检查；BSP 仅生成 3 个 zone（`BspMapGenerator.java:27`） | 部分线索只能靠面板搜证，地图探索不完整（不阻塞游戏，语义缺憾） |
| G1-6 | **重新生成联动**：地图 regenerate=true 可强制重生成（`ScriptGameService.java:501-502` + 前端「🔄 重新生成」`ScenePage.tsx:746-750`），但重生成剧本（重新 init）是新 session 新地图，两者无交叉联动 | — | 行为合理，无需改；仅记录 |

### 1.2 方案

**方案 A（最小，推荐先行）：自动串联，不内嵌 schema。**
- 后端：`ScriptGameService.initGame` 生成剧本、落库、快照后，追加一次 `generateMap(sessionId, "", 0, false)`（effTheme 自动取剧本名，clueLocations 自动取 game.clues 去重，全部现成）；失败自动 BSP 兜底（现有逻辑），不阻塞 init 成功返回（try-catch 吞掉仅记日志）。
- 前端：`ScenePage.genScript` 成功后已 `startScript(game)`，再补一行 `genScriptMap()` 或直接消费 init 响应里附加的 map（generateMap 结果并入 init 响应即可）。
- 效果：一次 init 出「剧本 + 地图」；地图仍独立存 mapData/快照，零 schema 变更、零表结构变更（守 D-013/D-014 纪律）。

**方案 B（完整）：内嵌进剧本 schema v1。**
- `ScriptSchemaV1` 增加可选 `map` 字段（宽容解析：缺失/非对象 → 不填，旧剧本零破坏；版本仍为 1，字段表追加说明）。
- 生成链路：`ScriptService.generateScript` 输出后合并地图（需给 ScriptService 注入 ScriptMapService 或改由 ScriptGameService 在 initGame 里把 map 写入 scriptSchema——后者的构造已持有 mapService（`ScriptGameService.java:321`），改动更小）。
- 落库：`persistScript` 增加 `content.put("map", ...)`（type=script 行随剧本带图）；快照继续带 map_data 双保险。
- 前端：init 响应/status 的 script 对象天然含 map，ScenePage 渲染无需单独 genScriptMap 调用；「生成地图/重新生成」按钮保留为覆盖入口（regenerate 时同步回写 schema 与快照）。
- 代价：**双 LLM 串行**（剧本 4000 tokens + 地图），一次 init 真实时长约 90-100s（现 scriptInit 前端超时已放宽到 120s，`client.ts:193` 注释，可承受但需 UI 提示）。

### 1.3 结论

**可行，完成度约 55-60%。** 后端地图生成全链路（端点/契约归一/7 项校验/重试/BSP 降级/缓存/快照落库）与前端手动入口已 100% 闭环（D-020 阶段 2 验收通过）；**缺口集中在「自动串联」「schema 内嵌」「BSP 对齐」三项（0%）与「LLM token 预算」一项（存疑）**。建议先做方案 A（0.5-1 人日）拿全自动体验，再评估方案 B；**G1-3（maxTokens=800）建议在任何 LLM 地图增强前先行实测确认并对照 D-023 提升至 2000-4000**——否则「LLM 生成地图」长期空转在 BSP 降级上。

**涉及文件（改动时）**：后端 `service/ScriptGameService.java`（initGame 自动 generateMap / schema 写回）、`service/ScriptMapService.java`（token 预算 + BSP 对齐，见调研项 4）、`service/ScriptSchemaV1.java`（+map 可选字段，方案 B）、`controller/ScriptController.java`（init 响应附加 map，可选）；前端 `components/ScenePage/ScenePage.tsx`（自动 genScriptMap）、`api/client.ts`（如新增批量端点）。**禁动文件**：无直接涉及；static 同步须主会话统一执行（既有先例）。

### 补.2 ScriptMapScene 瓦片渲染机制要点（可复用点）

- **运行时生成瓦片纹理**（`createTilesetTexture`，ScriptMapScene.ts:75-76）：契约 tileset 语义 = 5 格色块，**无素材依赖**——主地图渲染不依赖 tiles.png（tiles.png 仅阶段 0 验证 demo 占位素材）。
- **瓦片尺寸**：`m.tile_size || 32`（L66）；地图规模 ≤32×20 格（调研项 2 结论：无需 chunk 加载）。
- **碰撞层**：隐藏物理层已接入（角色不可穿墙），相机边界可直接取地图尺寸。
- **热点 zone**：金色区域 + 点击搜证 + `markZoneSearched` 变绿——即调研项 4「线索分配进地图」的现成交互底座。

### 补.3 与调研项 2/4 的可复用映射

| 新功能 | 直接复用 | 需新增 |
|---|---|---|
| 分块/区域 | `rooms[]/zones[]`（BSP 天然房间=区域） | 区域命名/标识 UI |

| 小地图 | rooms/zones 布局数据（DOM 覆盖层） | 小地图绘制组件 |

**结论**：瓦片系统不仅是「还能找到」，它就是当前剧本杀地图（LLM/BSP 双路径）的实际渲染底座——调研项 2 的三项增强（分块/相机/小地图）全部可直接在其上加，无重建成本。

## 二、调研项 2：地图分块分区域 + 相机跟随玩家视角 + 小地图界面

### 2.1 现状核实（证据）

**分块/分区域——数据层已天然具备：**
- 契约 v1 `rooms[]`（矩形区域，含 id/name/x/y/w/h/tags）与 `zones[]`（热点，含坐标/radius/clue_location）即为「区域 + 区域内交互点」结构（`docs/地图JSON契约-v1.md` §2 字段表）。
- BSP 生成器：递归二分叶子 → 每叶子一房间（`BspMapGenerator.java:91-114`），房间即天然区域，每房间一个 search zone（`:159-171`，zone 落在房间中心）。LLM 路径同样要求输出 rooms[] + zones[]（prompt `ScriptMapService.java:195-210`）。
- 前端已渲染房间名标注（`ScriptMapScene.ts:84-91`）与 zone 热点（`:119-129`、`:239-256`），「分区域」的**可视化基础已存在**；缺口只是**区域尚未参与玩法**（区域级线索分布/区域解锁/区域广播等，见调研项 4）。

**大图 chunk 加载是否必要？——当前规模下不必要。**
- 地图规模：BSP 默认 24×16 格（`BspMapGenerator.java:22-23`）= 768×512 px；LLM prompt 建议 20-32 × 14-20 格（`ScriptMapService.java:188`）≈ 最大 1024×640 px。瓦片数最多 640 个，Phaser 单 Tilemap 处理无压力（万级瓦片才需考虑）。
- 结论：**分块加载（chunk streaming）在 ≤32×20 格规模下是过度设计，留 P2**；仅在远期地图 ≥100×100 格或无缝大世界时启用（届时按房间粒度切 chunk 天然合适——rooms[] 边界即 chunk 边界）。

**相机跟随——现状没有，接入点明确：**
- 现状：`ScriptMapScene.create()` 里 `this.cameras.main.setZoom(scale)` + `centerOn(mapPxW/2, mapPxH/2)`（`ScriptMapScene.ts:70-73`），scale = min(800/宽, 560/高, 1.5)——**整图缩放适配，一屏全览，无 setBounds / startFollow / 用户缩放滚屏**。
- 接入点：同一 `create()` 内即可加 `this.cameras.main.setBounds(0, 0, mapPxW, mapPxH)` + `startFollow(this.player, true, 0.1, 0.1)`（`ScriptMapScene.ts:95` 已有 physics world bounds 同尺寸，语义一致）；玩家位置由 `update()` 的 WASD setVelocity 驱动（`:229-245`），跟随自动生效。
- **关键预埋**：HUD（提示条/标题）已 `setScrollFactor(0)` 固定屏幕（`ScriptMapScene.ts:136-144`）——相机滚动/缩放不会带跑 HUD；热点点击 `pointerdown` 用 `p.worldX/worldY`（`:151-153`），Phaser 已按相机矩阵做逆变换，缩放滚动后命中仍正确。风险点：缩放交互（滚轮 zoom）未实现，如需玩家控制缩放需补 wheel 事件 + zoom 上下限。

**小地图——现状没有，数据源现成：**
- 无任何 minimap/RenderTexture 用法（`roleplay-v4/frontend/src/phaser/` 全目录 grep `cameras` 仅 `ScriptMapScene.ts:72-73` 两处，无 RenderTexture）。
- 数据源：`mapData.ts` 的 `rooms[]/zones[]` 矩形 + `scene.player.x/y`（像素→格坐标换算 `÷tile_size`），信息完备。

### 2.2 三项可行性评估

| 子项 | 可行性 | 实现要点 | 工作量 | 风险 |
|---|---|---|---|---|
| 分块/分区域 | **高**（数据已有） | 玩法消费 rooms[]：区域级线索分布（调研项 4 方案）、区域名显示增强（当前已显示）、未来 chunk 以房间为界 | 玩法接入 0.5-1 人日；chunk 加载 0（当前规模不需要） | 无实质风险；避免为「分块」而分块 |
| 相机跟随 | **高** | `create()` 加 setBounds + startFollow(player)；可选滚轮 zoom（1x-2x）；HUD 已 scrollFactor(0) 无需改；玩家移动/碰撞零改动 | 0.5-1 人日 | 低：跟随开启后「整图一屏」观感变为「局部视野」，需同时保证地图默认尺寸小于视口时不抖动（follow 有 lerp 平滑）；hitTest 已兼容相机矩阵 |
| 小地图 | **高** | 方案 A：Phaser 第二 camera（ignore 全部场景对象）渲染到 RenderTexture，每帧贴屏角——引擎原生但代码略绕；**方案 B（推荐）：DOM/canvas 覆盖层**，读 rooms[]/zones[] + player 坐标画简化矩形图（房名/热点点/玩家蓝点/已搜证绿点），跟随玩家位置平移，0 引擎负担 | A：1-1.5 人日；B：0.5-1 人日 | 低：B 方案需在 React 组件层加一个 overlay div + 简单 canvas 或 SVG（样式/事件不冲突）；A 方案注意 RenderTexture 尺寸与相机 ignore 列表维护 |

### 2.3 结论

**三项均高可行。** 分区域是「数据已就位、玩法未消费」；相机跟随是「一行 setBounds + startFollow」级别接入（HUD 已预埋 scrollFactor(0)）；小地图推荐 DOM 覆盖层方案（数据源现成、独立于 Phaser 生命周期、与全屏方案天然兼容）。合计 1.5-3.5 人日。当前地图规模下**不做 chunk 加载**（记录为 P2 决策）。

**涉及文件**：`phaser/ScriptMapScene.ts`（相机跟随 + 缩放）、`phaser/PhaserScriptMapView.tsx`（小地图容器/按钮/props 透传）、新增 `phaser/MiniMap.tsx` 或 `components/MiniMap.tsx`（DOM 小地图）、`styles/global.css`（小地图定位样式）。禁动文件：无（注意 P-0802-P4 占用 ScenePage/ChatPage/client.ts/appStore.ts，本项不涉及）。

## 四、调研项 4：线索分配进地图的可行性探索

### 4.1 现状核实（证据）

**线索位置如何决定：**
- 线索 location 由 **LLM 剧本生成时指定**：`ScriptSchemaV1.buildPrompt`（`ScriptSchemaV1.java:46-74`）要求 clues[] 每条含 location（「所属地点」）；normalize 保留（`parseClues`）。兜底剧本固定 3 条（客厅/书房/花园，`ScriptSchemaV1.java:94-97`）。
- **无「clue.location ∈ locations[]」校验**：LLM 可能产出 locations[] 之外的 location（prompt 只给约束不给校验，normalize 不交叉检查）。

**地图热点如何绑定（一致性保障在哪）：**
- 第一道（软）：地图生成 prompt 注入 `clueLocations`（`ScriptMapService.java:178-194`），要求 zones[].clue_location 逐一取自线索地点。
- 第二道（硬，后置归一）：`bindClueLocations`（`ScriptMapService.java:124-152`）把 zone.clue_location 按 精确 → trim → 子串双向 → 同义词表 映射回剧本标准地点；**只对已存在的 zone 生效，不新建 zone**。
- 第三道（消费端）：前端热点搜证用 `zone.clue_location` 作 location 调 `POST /api/script/search`（`PhaserScriptMapView.tsx:52-62`）；后端 `search` 按 location 字符串精确匹配 clue（`ScriptGameService.java:426`）——**绑定链条 = prompt 软约束 + 字符串归一，无坐标级直接绑定**（契约 v1 无 zones[].clue_ids 字段，`docs/地图JSON契约-v1.md` §2）。

**地图上没有对应热点的线索会怎样（落空？）：**
- **不完全落空**：搜证有双通道——地图热点（`PhaserScriptMapView`）与 ChatPage 面板地点按钮（`ChatPage.tsx:507-513`，按 `state.locations` 列表渲染）。地图上无热点的线索仍可在面板按地点搜到。
- 但存在两个「地图侧落空」情形：① BSP 兜底地图 zone.clue_location=「房间 A」（`BspMapGenerator.java:107,168`）无法归一 → 地图点击搜证必返回「该地点没有更多可搜证线索」；② LLM 地图 zone 数 < 线索地点数（无覆盖保证）→ 部分地点地图无入口。

### 4.2 现状缺口清单

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G4-1 | **BSP 兜底地图 zone 与线索完全脱钩** | `BspMapGenerator.java:107,168`（「房间 A」/clue_location=房间名）+ `ScriptMapService.java:48-60` 同义词表无此类键 | 地图侧搜证必空手（面板不受影响）；BSP 路径（G1-3 若成立则高频出现）下地图玩法基本失效 |
| G4-2 | **无 zone 覆盖保证**：MapValidator 7 项不含线索覆盖率（`MapValidator.java` 全函数无 clues 概念） | LLM 自由发挥 zone 数量；BSP 固定 3 个 zone | 部分线索地点在地图上无入口；探索完整性缺憾 |
| G4-3 | **绿点状态不持久、双通道不同步**：markZoneSearched 仅改 scene 内存（`ScriptMapScene.ts:60-66` zoneStates）；服务端只记 playerClues（`ScriptGameService.java:154,470`），不记「哪些地点/zone 已搜过」 | 面板搜证不会让地图热点变绿；地图重挂载/切页后绿点丢失 | 玩家重复探索困惑；与 C3/D-017 快照纪律比缺「搜证足迹」持久化 |
| G4-4 | **分配策略缺失**：zone↔线索地点映射完全交给 LLM 自由发挥（仅 prompt 软约束 + 后置归一），无随机/均衡/剧情关键点策略 | `ScriptMapService.java:81`（prompt 内嵌）| 质量不可控，跨次生成分布漂移 |
| G4-5 | **转交线索后地图无表现**：地图不渲染线索/归属；转交只改 ownership（`ScriptGameService.java:546-580`）与面板 my_clues | — | 地图是纯空间探索层，与持有状态脱节（可接受，属增强项） |
| G4-6 | **线索可见性**：未发现线索在地图上不显示内容（只有金色热点），搜证后才在结果卡看到；公开线索（public=true）恒可见但地图不区分 | `ScriptMapScene.ts:239-256`（热点只有金/绿两态）| 符合预期，可作为增强（见 4.3-E） |

### 4.3 改进方案（按优先级）

- **A. 生成后覆盖 pass（推荐先行，后端最小改动）**：`ScriptMapService.generateMap` 返回前对 zones 做覆盖补齐——对每个 distinct clue location，若当前无 zone 的 clue_location 归一后等于它，则自动补一个 search zone（落在最近的 walkable 房间中心或走廊中点，radius 1，id=`z_auto_<location>`）。**一个 pass 同时解决 G4-1（BSP 地图也被覆盖）与 G4-2（LLM 缺 zone）**；BspMapGenerator 无需改动。工作量 0.5-1 人日 + 测试（对齐 MapValidator 6/7 校验项，自动补的 zone 必须可通行——由放置算法保证）。
- **B. 搜证足迹持久化（P1）**：ScriptGame 增加 `playerSearchedLocations`（或复用 playerClues 推导「该地点已无可搜线索」），进快照 contentJson（守 D-017 纪律）与 toMap 附加键；前端挂载地图时按足迹初始化 zoneStates 恢复绿点；面板搜证成功也回写足迹 → 双通道绿点同步。工作量 1-1.5 人日。
- **C. 契约 v2 直接绑定（P2）**：`zones[].clue_ids` 可选字段（地图生成后按 location 匹配回填），前端搜证改按 clue_id 直取而非字符串匹配——根治一致性问题。工作量 1-2 人日（契约文档 + 校验 + 前后端）。
- **D. 分布策略（P2）**：覆盖 pass 内做地点均衡（每线索地点恰好 1 个 zone，密集区可合并为「一 zone 多地」搜证语义不变）。
- **E. 可见性增强（P2）**：地图热点三态——未搜证金 / 已搜空灰 / 已获线索绿 + 转交后持有者标记（需 B 的足迹 + 地图渲染线索归属）。

### 4.4 结论

**可行，完成度约 50-60%。** 字符串绑定链路（prompt 注入 → bindClueLocations 归一 → 热点搜证）已闭环且可玩；**核心缺口是「覆盖保证」（G4-1/G4-2）与「状态持久化」（G4-3）**。最小改进 = 方案 A（覆盖 pass，0.5-1 人日）即可让「每条线索在地图上可被找到、BSP 兜底也可用」；完整体验 = A+B（+C/D/E 按需）。方案 A 与调研项 1 的 G1-4 是同一改动的两个受益面，建议合并派单。

**涉及文件**：后端 `service/ScriptMapService.java`（覆盖 pass + 放置算法）、`service/ScriptGameService.java`（搜证足迹，方案 B）、`simulation/map/BspMapGenerator.java`（可选不动）、`docs/地图JSON契约-v1.md`（方案 C 契约修订）；前端 `phaser/ScriptMapScene.ts`（绿点初始化，方案 B）、`phaser/PhaserScriptMapView.tsx`（足迹 props，方案 B）。禁动文件：无。

### 统计口径

- **范围**：本次地图调研主链路 = 父会话（`ac10d609`，自 08-02 16:23 UTC 地图调研发起起）+ 当前会话（`f1e512f3`）。地图调研 researcher 子会话的转录已被 OpenClaw 按子会话清理策略删除，无法纳入（主会话已含其报告接收/整合/归档全过程，覆盖度 ~90%）。
- **指标定义**（DeepSeek usage 语义）：
  - `input` = 未命中缓存的**新增输入**（本轮真正的新内容）；
  - `cacheRead` = **缓存命中**的重复传输内容（系统提示 + 工具定义 + 历史消息，每轮全量重发）；
  - 单轮总输入 = input + cacheRead。
- **四类垃圾界定**：
  - **填充垃圾** = 每轮固定重复的模板：系统提示 + 工具定义 + 注入文件（AGENTS/SOUL/MEMORY/TOOLS/USER/IDENTITY/HEARTBEAT）；
  - **冗余** = 内容级精确重复消息（同工具同文本再次出现，如 poll 循环）；
  - **无效输入** = 失败/空结果消息（SIGKILL、Traceback、超时、空输出）；
  - **噪声** = 心跳/无关系统事件注入。

|---|---|---|---|

### 填充垃圾构成拆解（单轮 28,157 tokens）

| 组成 | tokens | 说明 |
|---|---|---|
| 注入文件（7 个工作区 md） | ≈ 4,645 | 10,220 chars ÷ 2.2 |
| **工具定义 + 系统框架** | ≈ 23,500 | **最大单项填充**：40+ 工具的 JSON schema 每轮全量重发 |
| 首条用户消息 | ≈ 30 | 可忽略 |

### 关键结论

1. **内容本身是干净的**：消息级分类中有效字符占 99.4%，真正的"内容垃圾"（冗余+无效+噪声）合计仅 ~0.5%。
2. **输入爆炸的主因是上下文全量重传**：97.1% 的输入是每轮重复发送的（系统模板 + 全部历史），单轮平均输入 121,574 tokens，其中只有 2.9% 是新内容。
3. **填充垃圾 ≈ 23.2%**，其中工具定义（~23.5K tokens/轮）是最大单项——40+ 工具 schema 无论用不用都全额进上下文。
4. **缓存是冗余传输的经济对冲**：97.1% 缓存命中使实际成本仅为全价重算的 ~6%（$0.0535 vs $0.87），但 tokens 配额/延迟仍按总量计。
5. **可优化方向**（不阻塞业务）：① 工具按需注入/分组注入（砍掉最大填充项）；② 长会话上下文压缩或分段（历史重传 74%）；③ 避免 poll 循环与失败命令重试（本次 SIGKILL 的全盘搜索即为无效输入实例）。

> 口径说明：token 换算（字符÷2.2）与固定模板估算为近似值；「必要上下文重传」为重复传输扣减固定模板后的余量，实际含系统注入的动态部分，误差 ±5%。
