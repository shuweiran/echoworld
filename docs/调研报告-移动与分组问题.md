# 问题 1：2D 地图里控制角色移动的能力几乎没有

## 1.1 复现路径（代码层面）

项目存在**两套互不相干的"2D 地图"**，移动能力问题在两个场景表现不同：

### 场景 A：2D 模拟（一般模式 general+explore，Phaser `SimulationScene`）

```
1. GameBridge explore 分支挂载 PhaserSimulationView（frontend/src/demo2/pages/GameBridge.tsx L212-224）
   → Phaser 场景 SimulationScene（PhaserSimulationView.tsx L263，构造传入 playerName、map）
2. 玩家点击地图画布 → SimulationScene.create() 注册的 pointerdown（SimulationScene.ts L233）
   → 解析"受控角色 me"（L248-254：playerName → 'me'/'我'/'主人' → names[0] 兜底）
   → 回调 onSetTarget(me, x, y)（L259）
3. PhaserSimulationView.onSetTarget（PhaserSimulationView.tsx L156-163）
   → fetch POST /api/simulation/target/{agentName}，body {x, y}
4. 后端 SimulationController.setTarget（SimulationController.java L200-216）
   → state.setTargetX/Y + setHasTarget(true) + setManualTarget(true)（L214，60s 有效）
5. SimulationWorld.tick 每 200ms（SimulationWorld.java L19/L180-197）：
   preTickHooks（applyMovementConstraints L570 / applyScheduleWindows L196）→ MovementSystem.update（L192）
6. MovementSystem.update（MovementSystem.java L54-84）：
   manualTarget 保留 → computeForce 目标力 TARGET_WEIGHT=50 牵引角色走向目标
   → 到达（tdist<5）clearTarget（L116-118）→ 无目标且合力小时 WANDER_STRENGTH=15 随机游走（L136-139）
7. 60 秒后：SimulationService.applyDirectorDecisions（SimulationService.java L694-700）
   manualTarget 超时 → setManualTarget(false)，导演（LLM）/日程/轨道约束恢复接管
```

结论：**链路存在但体验极弱**——只有"一次性点击到达"，无持续方向控制、速度慢、无寻路、60s 后失去手动标记。

### 场景 B：剧本杀地图（Phaser `ScriptMapScene`，PhaserScriptMapView）

```
1. PhaserScriptMapView 挂载 ScriptMapScene（PhaserScriptMapView.tsx L210）
2. WASD/方向键本地移动（ScriptMapScene.ts L370 注册 W,A,S,D,UP,LEFT,DOWN,RIGHT；L515-528：
   this.player.setVelocity(vx * speed, vy * speed)，speed=150 px/s 纯 Phaser arcade 物理）
3. 移动结果仅经 onPlayerMove 回调格坐标（ScriptMapScene.ts L570-576）
   → PhaserScriptMapView L209 setPlayerPos → MiniMap 小地图消费（L305）
4. 全程无后端调用：不上报 /api/simulation/target，无权威同步，AI 角色（aiCharacters）
   不参与该移动系统
```

结论：**剧本杀地图的"移动"是纯前端本地漫游**，无任何机制/同步意义。

## 1.3 根因分析

| 根因 | 确定性 | 说明 |
|---|---|---|
| **R1：2D 模拟无键盘/持续方向控制，只有一次性点击** | **确认** | SimulationScene 全文无 keyboard 绑定（证据 A1/A11）；点击=走到指定点，到达即停（A8），之后只剩微弱随机游走（A9）。"控制移动的能力"=一次点一下走一步 |
| **R2：移动速度被调慢** | **确认** | P-0813-F 为降 AI 对话密度把 move-speed-base 从 50 降到 45、随机幅度 60→35（A10，DECISION_LOG D-029 无此记录但 yml 注释写明"原 50+rand×60"）。45-80 px/s 在 1000×600 世界里横穿要 12-22 秒，主观"几乎不动" |
| **R3：无寻路，障碍把角色卡死/抖动** | **确认** | MovementSystem 是纯力导向（A15）：直线目标 + blocked 切向滑行（力 100）+ 障碍斥力 200（A7）。目标力仅 50，障碍斥力 4 倍于目标力——LLM 瓦片地图墙/家具密集时，角色在墙前被推回、抖动、无法绕行到达目标 |
| **R4：手动目标 60s 超时被夺回控制权** | **确认** | MANUAL_TARGET_HOLD_MS=60_000（A5），超时后 setManualTarget(false)（A6），导演/日程/轨道约束恢复接管。**若玩家未选玩家角色**（playerName 为空 → me=names[0] 兜底控制第一个 AI，A2），60s 后该 AI 完全回归 AI 自主（导演 LLM 决定/轨道约束/日程窗口），玩家失去控制 |
| **R5（场景 B）：剧本杀地图移动是纯前端本地漫游，无后端权威同步** | **确认** | WASD 走 Phaser arcade 本地物理（A12），坐标只喂小地图（A13/A14），从不调用 /api/simulation/target。AI 角色不参与、无机制效果、多玩家互不可见对方移动 |
| **R6（推断）：点击与移动的"手感"断连** | **推断** | 前端 SSE world_snapshot 200ms + 渲染层插值（P-0813-G），但后端 200ms tick、速度 45-80px/s、到达 5px 阈值，点击→起速→到达全程 1-2s 起步；无即时反馈感 |

> 注：坐标系统**未错位**——前后端同用 1000×600 世界且瓦片地图同缩放（`Obstacle.fromCollisionGrid` L106-107 `tileW=1000/w, tileH=600/h` 与前端 `drawTileMap` 的 `WORLD_W/W、WORLD_H/H` 一致），排除"像素 vs 网格坐标混用"假设。

## 1.4 修复方向建议（只给方案，不实施）

1. **2D 模拟增加 WASD/方向键持续控制**：SimulationScene 注册 keyboard，方向键按住 → 高频（如每 100-200ms）POST `/api/simulation/target`（或新增 `/move-dir` 端点设相对位移/速度向量）；与点击目标互斥/叠加（点击=目的地，方向键=临时覆盖）。
2. **移动速度回升或配置化**：`move-speed-base` 提高（如 70-90）或对玩家角色单独提速；P-0813-F 的降速针对 AI 密度，可只对 AI 生效。
3. **MovementSystem 加轻量寻路**：基于障碍网格做 BFS/A* 或势场导航（`Obstacle.fromCollisionGrid` 已有瓦片网格），替代"直线+切向滑行"；或至少提高 TARGET_WEIGHT（50→150+）使目标力 > 障碍斥力（200），并让 blocked 时沿墙绕行而非原路弹回。
4. **manualTarget 语义修正**：玩家角色（playerControlled）本就免接管（applyDirectorDecisions L695 跳过、MovementConstraint.apply 跳过、SchedulerService 跳过），问题在"兜底控制第一个 AI"路径——前端无玩家角色时禁止点击控制 AI（或明确提示"导演模式不可控制"），避免 60s 后失控错觉。
5. **剧本杀地图**：明确"本地漫游"定位（UI 提示），或按需求接入后端权威移动（ScriptMapScene 格坐标 → 后端对局状态），属较大改造，建议先确认产品意图。

# 问题 2：分组逻辑混乱

## 2.1 复现路径（代码层面）

```
1. ConversationManager.tick（ConversationManager.java L431-485）每 tick：
   - 全场景听力计算：HearingSystem.computeAudibility（L434）
   - 排除玩家角色（L441-444：playerControlled 不进自动建组）
   - ModeClassifier.classify(hearing, available)（L466）→ 建组候选
2. ModeClassifier.classify（ModeClassifier.java L52-105）：
   - 取 canHear 的听对 → 建无向图邻接表（L56-60）
   - findConnectedComponents 求**连通分量**（传递闭包，L84-105）
   - 分量 ≥2 人且愿意说话 → GroupCandidate → ConversationManager.startGroup
3. 组 ID = 成员名排序 join "+"（ModeClassifier.GroupCandidate.groupId() L123-127）——纯名字串，无距离/类型语义
4. 玩家侧：
   - 手动加入：POST /api/simulation/group/{groupId}/join → ConversationManager.joinGroup（L362-386）
     校验链 = 组存在→活跃→玩家在场→未在组→未满；**无任何距离校验**
   - 自动 DYAD：玩家发消息 → tick 内与"最近"AI 建组（L456-466）——nearest 无最大距离上限
5. 轨道（谁知道什么）分配：SimulationOrchestrator.tick（SimulationOrchestrator.java L60-66）
   → trackDirector.assign(全场景 agents, goals)
   → TrackDirectorService.assign（L94-127）：
     无敏感触发且无冲突 → allMerged(全场景)（L110-113/L128-142）——**全员两两互见，不看距离**
     score≥40（≥5 人必触发）→ SpatialTrackResolver.resolve（conversationDistance=5.0）
6. MovementConstraint.computeMerged（MovementConstraint.java L170-215）：
   MERGED 组成员 → leader 收敛组质心 + follow slot 直线队形 → **相距很远的成员被物理拉到一起**
```

## 2.3 根因分析

| 根因 | 确定性 | 说明 |
|---|---|---|
| **R1：分组=听力连通分量传递闭包，链式传递无距离上限** | **确认** | 分组只看 `canHear` 连通性（B1/B2）。A↔B↔C↔D 链式可听（每对 80-130px）→ A 与 D 相距 400px+ 也进同一组（GROUP_DISCUSSION）。"很远的地方都能一组"的**直接机制**。有效可听距离由距离平方衰减决定（B4），但组件内**没有组直径/成员对距离上限检查** |
| **R2：无"组类型"概念——AI 组 / AI / 用户组混为一谈** | **确认** | 组只有 ConversationMode（DYAD/GROUP_DISCUSSION/DEBATE/PUBLIC_SPEAKING）语义（B13），**没有 AI 自动组 vs 用户加入组的类型字段**；participants 是纯名字数组，不含 playerControlled 标记（B13）；玩家加入后与 AI 同构混在组里，前端无法区分"AI 组"与"用户组" |
| **R3：joinGroup 无距离校验——玩家在世界任意角落可加入任意组** | **确认** | 校验链只有存在/活跃/在场/未重复/未满（B5）。前端 UI 用 findApproachableGroups 做了"接近才显示按钮"（PhaserSimulationView/simulationData.ts），但**后端不校验**，直接调 API 即可远程入组；前端限制只是展示层掩盖 |
| **R4：玩家自动 DYAD 无距离上限** | **确认** | 玩家发消息→与"最近"AI 建组，nearest 无最大距离（B6）。玩家在地图一角，最近的 AI 在几百 px 外也会被拉进 1v1 组 |
| **R5：Track 分配输入=全场景，无冲突时全员 MERGED（互相"可见"）** | **确认** | SimulationOrchestrator 把全场景 agent 一次性喂给 assign（B9）；score 未触发且无冲突 → allMerged 全员互见（B10/B11），**与距离完全无关**。配合 B12，MERGED 组被 MovementConstraint 物理拉到 leader/质心——"很远的地方都能一组"的第二机制（先"互见"，再"物理聚拢"） |
| **R6：距离单位混用（"格" vs px）** | **推断** | SpatialTrackResolver.DEFAULT_CONVERSATION_DISTANCE=5.0 注释为需求文档"5 格"（B8），但世界坐标是 px（1000×600）；legacy 路径直接当距离用（B7）→ 5px≈贴脸。主路径（TrackDirectorService 默认构造 `new SpatialTrackResolver()`）同值。5px 阈值使"近距离对话（MERGED）"几乎永不触发（除完全重叠），而 ≥5 人局因人数因子 40 必然触发空间分配 → 全员 WEAK/ISOLATED |
| **R7：近距分组检查常量存在但未接线** | **推断** | ModeClassifier.CLOSE_THRESHOLD=150.0 定义了从未使用（B14），暗示原设计有"近距才组队"的意图未实现 |

> 汇总一句话：**分组无"组内空间直径上限 + 组类型 + 距离门槛"三重缺失**——听力传递闭包导致空间上无限延伸成组；无组类型字段导致 AI/用户混同；join/DYAD/全场景 MERGED 三处无距离校验导致"人在千里外也能一组"。

## 2.4 修复方向建议（只给方案，不实施）

1. **连通分量加空间聚类**：ModeClassifier 分组时增加"组内任意成员对距离 < 阈值（如 250-300px）"或按空间格聚类（SpatialGrid 已有），禁止链式无限传递；`CLOSE_THRESHOLD=150` 可作为默认阈值接线。
2. **新增组类型字段**：ConversationGroup 加 `kind`（AI_AUTO / USER_JOINED / SCRIPT_DISCUSSION / WEREWOLF_DISCUSSION 等）+ participants 项附 `isPlayer` 标记；getStatus 下发，前端按类型/玩家标记分组展示。
3. **joinGroup 加距离校验**：后端校验玩家与组中心或最近成员距离 < 阈值（对齐前端 findApproachableGroups 的 100-120px），超距拒绝；玩家自动 DYAD 同样加 `MAX_AUTO_DYAD_DISTANCE`。
4. **TrackDirectorService.assign 改按听觉组分分配**：SimulationOrchestrator.tick 不再全场景 allMerged，改为对每个活动组 + 每个听力连通分量分别 assign；无触发时 MERGED 也只覆盖同分量成员。
5. **单位修正 + 阈值配置化**：SpatialTrackResolver 的 conversationDistance 明确为 px 并给合理默认（如 60-80px），配置键 `roleplay.track.conversation-distance`（对齐 D-004 勿 hardcode 纪律）。
6. **MovementConstraint.computeMerged 加距离守卫**：成员与 leader 距离超过阈值（如 300px）时不强制归队（或先 WEAK 靠近再 MERGED），避免"瞬移式聚拢"的突兀表现。
