## 0. 结论速览（一句话版）

- **断点结论**：玩家进不去他人轨道的根因是**链路两端都缺**——后端 `ConversationManager` 把玩家角色从自动建组候选**硬排除**（tick L164），且**全后端没有「把某成员加入已存在群组」的任何方法/端点**（grep 全项目零命中 joinGroup/addParticipant）；前端 2D 视图**只有「点击设目标 + 以玩家身份发言」两个交互，没有任何「加入某角色/某组的聊天轨道」入口**（grep join/加入 零命中）；玩家发言只能与**最近的一个空闲 NPC** 新建一对一的 DYAD 组（tick L180-183），既进不了多人讨论组，也进不了正在对话中的 NPC 组。
- **方案一句话**：推荐 **方案 A（点击群组/角色「加入对话」→ 后端新增 join 能力把玩家纳入组）** 为主、**方案 B（靠近自动进组，改 playerControlled 跳过逻辑 + 配置开关）** 为辅，两者共用同一个后端「成员加入组」原语；方案 C（轨道列表 UI）是 A 的另一种前端形态。

## 2. 玩家角色（playerControlled）在轨道系统中的特殊处理（关键）

> 这是「用户进不去」的核心，全部有行号证据。

### 2.1 玩家角色怎么被标记

- `AgentState.playerControlled` 字段（AgentState.java:29），默认 false。
- 标记点：`SimulationService.initWithPersonas`（SimulationService.java:217-224）——显式 `player_name` 同名、`player_id` 解析名（P-0802-P2）或旧规则名字 "me" 命中 → `setPlayerControlled(true)`；`renamePlayerCharacter` 改名后重新断言（L244）。

### 2.2 玩家怎么被排除在「自动邻近对话组」之外（三个排除点）

| # | 位置 | 证据 | 效果 |
|---|---|---|---|
| 1 | ConversationManager.tick 收集候选 | **L164** `if (s.isPlayerControlled()) continue;` | 玩家角色**从不进入 `available` 集合**（自动建组候选池） |
| 2 | ModeClassifier 成员过滤 | ModeClassifier.java:56-60（`!s.isInConversation()`）｜候选组源自 `available`（tick L188 传入） | 玩家不在候选里，连通分量**永远不会包含玩家** |
| 3 | 玩家发言找「最近 NPC」时 | tick **L176** `if (a.isPlayerControlled()) continue;` | 玩家只能找 **NPC** 对话，不会找另一个玩家角色 |

### 2.3 玩家发消息时怎么进 DYAD 组（唯一入口）

```
ConversationManager.tick (L168-184)
  条件：玩家角色 isPlayerControlled && currentMessage 非空 && 不以 "(主控" 开头（L170-172）
  动作：在 available（非玩家、非忙碌 NPC）中找最近 NPC（L174-179）
        → startGroup("玩家+NPC", ConversationMode.DYAD, [player, nearest])（L180-183）
  后续：executeRound 中玩家跳过 LLM，直接把 currentMessage 作为本轮发言（L346-354）
```

**要点与限制（证据）**：
1. **只进 DYAD**：`ConversationMode.DYAD` 走 `DyadStrategy`（ConversationManager.java:183 + init 注册 L140-142），**DyadStrategy 不消费 trackAssignments**——即玩家参与的对话组**不经过 TrackStrategy 的 MERGED/WEAK/ISOLATED 上下文隔离**（TrackStrategy 只注册给 GROUP_DISCUSSION 和 DEBATE，L143-145）。轨道分配对玩家参与的组「算而不吃」。
2. **只找空闲 NPC**：`available` 排除了 `isBusy`（L193-199 定义 isBusy：inConversation 或已在活动组）——**正在对话中的 NPC 不会成为玩家的对话对象**，玩家无法插入一个进行中的讨论组。
3. **新建而非加入**：即使 NPC 就在附近对话，玩家发言也是**新建一个组**（groupId = 玩家+NPC），不是加入现有组。
4. **玩家在组内不生成**：executeRound L346-354 玩家角色直接用自己的消息，AI 不代声；玩家无消息时输出 "..."（L350）。
5. 全项目 grep `joinGroup / addParticipant / joinTrack / addMember`：**零命中**——后端没有「向已存在群组加入成员」的任何能力。

### 2.4 玩家在其他层的特殊处理（辅助证据）

- `SimulationService.runDirectorRound` L495：主控不给玩家生成目标/行动（`if (state.isPlayerControlled()) continue;`）。
- `buildDirectorPrompt` L598：prompt 明确「玩家亲自控制，不要生成决定」。
- `MovementConstraint.compute` L138：`playerControlled` 或 `manualTarget` 的移动不被轨道约束覆盖（D-006：约束是边界不是牢笼）。
- `ConversationManager` L151 有 `PLAYER_AGENT_NAME = "me"` 死常量（未使用，玩家判定已全部走 isPlayerControlled()，无残留硬编码风险）。

## 4. 断点定位：用户无法进入他人轨道的具体原因链

**结论：不是单一断点，是「后端无能力 + 前端无入口 + 既有判定路径主动排除」三环叠加。** 距离/阈值判定不是主因（主因是玩家被主动排除在候选之外）。

```
原因链（可画因果链图）：

[A] 后端无「加入现有组」能力
    ├─ ConversationGroup 成员表是 LinkedHashMap，无 addParticipant 方法（ConversationGroup.java:57-58）
    ├─ ConversationManager 无 joinGroup/加成员 API；群组成员在建组时一次性固定（startGroup L223）
    └─ 无任何 REST 端点支持加入（SimulationController 端点清单零命中）
        → 即使前端想点「加入」，也没有后端可调

[B] 前端无「加入」入口
    ├─ SimulationScene pointerdown 只做「移动自己」（L150-169），群组框无交互（applyGroups 仅绘制）
    ├─ 聊天面板只有「以玩家身份发言」（sendChat）
    └─ SimGroup 类型不含 id（前端拿不到组标识可传后端）
        → 用户没有任何「进入某角色/某组聊天轨道」的操作

[C] 既有自动路径主动排除玩家（即使不加任何代码，靠近也不会进）
    ├─ ConversationManager.tick L164：playerControlled 不进 available（自动建组候选）
    ├─ ModeClassifier 候选组永远不含玩家
    └─ 玩家发言 → 只能与「最近的一个空闲 NPC」新建 DYAD（L180-183），
        且 DyadStrategy 不消费轨道分配（玩家组的 MERGED/WEAK/ISOLATED 算而不吃）
        → 「靠近自动进组」与「发言进组」两条路都被设计性地挡死

[D] 判定细节（次要因素）
    ├─ SpatialTrackResolver 会话距离 5 格 / 听觉范围 180-260px（AgentState hearRange，SimulationService.initDemo L120）
    └─ InteractionDetector 阈值 40 只决定「组内」轨道模式（MERGED/WEAK/ISOLATED），
        不决定「玩家能否进组」——进组与否由 tick 的 available/候选逻辑决定
```

**一句话**：D-027 里「玩家主动发言才进 DYAD 组=在场真实生效」被确认是**设计语义（非 bug）**，但**「进他人的组」这个能力从设计上就不存在**——2D 世界的轨道/讨论组是 NPC 之间的空间社交，玩家是旁观者，只能 1v1 拉人，不能进群。

## 5. 改进方案（2-3 个，对比表）

> 三个方案共用同一个**后端原语**：`ConversationManager.joinGroup(groupId, playerName)`（把玩家纳入现有组 + 重算轨道 + 玩家消息注入轮次）。区别只在「触发方式」。

### 方案 A：点击角色/群组「加入对话」+ 后端 join 能力（推荐主方案）

- **用户路径**：2D 中点击群组框或某 NPC → 弹出「💬 加入对话」→ 玩家角色进场（组框加玩家、气泡出现、可发言）。
- **后端改动**：
  1. `ConversationGroup` 新增 `addParticipant(AgentState)`（成员表插入 + engagement 初始化 + unfreeze）。
  2. `ConversationManager` 新增 `joinGroup(String groupId, String playerName)`：校验组存在且活跃 → addParticipant → 玩家 `setInConversation(true)`+冻结 → `trackDirector.assign`（或 SpatialTrackResolver）**重算组内全部成员的 trackAssignments**（玩家按距离判定 MERGED/WEAK/ISOLATED，与 NPC 同等对待）→ 返回组信息。
  3. 玩家进组后的**发言注入**：现有 executeRound 已支持玩家角色读 currentMessage（L346-354），但轮次由后台 while 循环驱动（L283-292，cooldown 2-3s）——需在 tick 或 executeRound 内补「组内玩家有 currentMessage → 立即触发一轮」的消费点（或在 join 时把玩家设为当前发言者，下一轮自然消费）。这是方案 A 唯一需要新写的机制。
  4. 新增端点 `POST /api/simulation/group/{groupId}/join`（body: player_name）+ 可选 `POST /api/simulation/group/{groupId}/leave`。
  5. 玩家离组：组解散或 leave 时还原（inConversation=false + 从 participants 移除 + 重算轨道）。
- **前端改动**：SimulationScene 群组框/角色增加点击命中 + 「加入对话」按钮（或角色右键菜单）；SimGroup 类型补 `id`；client.ts 加 join API；加入后本地提示。
- **工作量粗估**：后端 1-1.5 人日（含 join 原语 + 发言注入机制 + 2-3 个测试）；前端 0.5-1 人日。
- **风险**：① 玩家进 GROUP_DISCUSSION 后会被 TrackStrategy 按轨道模式给上下文——若玩家被判 WEAK/ISOLATED，会拿到「摘要/独白」而非全文，需明确「玩家进组是否豁免隔离」（建议：玩家进组语义=主动参与 → 玩家恒 MERGED 视角，或按轨道照实执行，二者需拍板）；② 组循环是后台线程，join 与 executeRound 并发——需同步保护（组对象操作加锁或与 dissolve 竞态处理）；③ DyadStrategy 组加入多人会变语义（DYAD 组应禁止 join，或 join 时升格为 GROUP_DISCUSSION）。
- **对现有 Track 语义的影响**：低——不改变 NPC 侧任何判定；仅新增「玩家也是组成员」这一种输入形态；玩家在组内按轨道隔离规则参与（或豁免，见风险①）。

### 方案 B：靠近自动进组（改 playerControlled 跳过逻辑）

- **用户路径**：玩家角色走近一组正在聊天的 NPC → 自动进入该组（气泡、可发言）。
- **后端改动**：ConversationManager.tick L164 改为「默认排除、开关开启时纳入」——玩家进入 available 后，ModeClassifier 连通分量自然包含玩家（L188 传入 available）；需处理玩家无消息时的占位噪音（executeRound L350 现在输出 "..."）；玩家发言仍走 currentMessage 消费。
- **工作量粗估**：后端 0.5-1 人日（改 tick 过滤 + 占位策略 + 测试）；前端几乎零改动（在场判定/组框已就绪）。
- **风险**：① 玩家被**被动**拉进组（AI 主导），可能打断玩家自由移动/观察——与「玩家是上帝视角还是化身在场」的产品语义冲突；② 玩家进组后 MovementConstraint 冻结（startGroup L276-279），玩家无法移动=可能被困在组里直到组解散（30s idle）；③ 「发言也建 DYAD」与「自动进组」双路径可能互斥/打架（玩家已在组内时 L168-184 的 DYAD 逻辑需跳过）。
- **对现有 Track 语义的影响**：中——直接改掉 D-027 确认的「玩家不进自动邻近组」设计语义，需配置开关兜底（默认关）。

### 方案 C：轨道/讨论组列表 UI 选择加入

- **用户路径**：2D 视图侧边「📡 轨道/讨论组」面板列出活动组（mode/成员/话题/轮次，数据源 conversation-status + track/state 已有）→ 点「加入」→ 走方案 A 的 join API。
- **改动**：前端新增列表面板（0.5 天）+ 后端同方案 A（join 原语）。
- **工作量**：后端同 A；前端比 A 多 0.5 天（列表面板）。
- **风险**：同 A；额外——多组并发时「加入哪个组」的信息负担（列表信息越多越好选，但 2D 沉浸感打折）。
- **Track 语义影响**：同 A。

## 6. 可配置化建议（新增开关接线）

### 6.1 建议配置键

```
roleplay.track.player-join: "off"      # off=现状（默认，玩家不参与任何组）
                                       # click=方案A（点击群组/角色加入）
                                       # proximity=方案B（靠近自动进组）
roleplay.track.player-join-track: "merged"   # 可选：玩家进组后的轨道模式
                                             # merged=玩家恒 MERGED 视角（推荐）/ auto=按距离与 NPC 同判
```

### 6.2 接线模式（对齐既有双轨先例）

项目内**两种**既有接线方式，任选其一（或都做，见 D-018/D-027「服务层 @Value 与 AppConfig 同源同值」先例）：

1. **AppConfig 模式**（推荐，主配置源）：
   - `AppConfig.java`（config/AppConfig.java:26-34 嵌套结构）：`GameConfig` 内（或新建 `TrackConfig`）加字段 `playerJoin = "off"` + `getPlayerJoin/setPlayerJoin`，仿 `BroadcastConfig.speechMode`（AppConfig.java:222-226 字段 + setter 尾部）。
   - `application.yml`（roleplay: 下，L29 起）加键 + 注释；`application-test.yml` 同键（对齐 D-022「yml 双份」纪律）。
   - 消费方：SimulationService 构造器注入 AppConfig（已是构造注入，SimulationService.java:92-98）→ 传给 ConversationManager（init 或 setter，仿 `setSpeechBroadcastListener` / `setTrackDirector` 模式，ConversationManager.java:95-101）。
2. **@Value 模式**（参考先例）：
   - RouterService.java:74-75 `@Value("${roleplay.round.serial:false}") private boolean serialRound;` ——若只在 ConversationManager 一处消费，可直接在 SimulationService 或 ConversationManager 加 `@Value("${roleplay.track.player-join:off}")`。

**开关作用点**：
- `off`：tick L164 保持排除（现状）。
- `click`：tick 不变；前端调 join 端点（5.1 方案 A）。
- `proximity`：tick L164 改为纳入玩家进 available（5.1 方案 B），且 L168-184 的玩家 DYAD 路径在玩家已入组时跳过。

**测试纪律**：对齐 D-004「阈值勿 hardcode」——新增开关默认值走 yml 双份 + 测试用显式 setter（仿 `setSerialRound`，RouterService.java:818-819）；边界用例锁定三值行为。
